HMWK 2 — From Wallet Seed to Ethereum Address

Hashing, Key Derivation, and Cryptographic Primitives in the Ethereum Ecosystem

1. The Practical Cryptographic Pipeline in Ethereum Wallets

Ethereum wallets follow a structured, deterministic pipeline to convert human-readable mnemonics into a cryptographically secure address. The simplified workflow proceeds as follows:

Mnemonic (BIP-39) ↓ Seed (BIP-32 / BIP-44) ↓ Private Key (secp256k1) ↓ Public Key (secp256k1) ↓ Ethereum Address (Keccak-256) ↓ Checksummed Address (EIP-55)

Role and Purpose of Standards and Primitives:

  • BIP-39: Converts a random entropy bit-sequence into a human-readable mnemonic sentence (usually 12 to 24 words) and derives a binary seed.
  • BIP-32: Introduces Hierarchical Deterministic (HD) wallets, allowing an entire tree of key pairs to be generated from a single root seed.
  • BIP-44: Defines a standard derivation path structure for multi-account and multi-coin wallets (e.g., m/44'/60'/0'/0/0).
  • secp256k1: An elliptic-curve standard that defines the algebraic relationship between private and public keys and enables digital signatures via ECDSA.
  • Keccak-256: A cryptographic hash function applied to the public key to derive the truncated 20-byte Ethereum address.
  • EIP-55: Mixed-case checksum encoding implemented to detect human typographical errors in Ethereum addresses.

2. Key Conceptual Distinctions

To fully understand the architecture, it is essential to distinguish between the following core concepts:

  • Key Generation vs. Key Derivation: Generation creates foundational secret material randomly using system entropy, whereas derivation uses deterministic functions (such as HMAC-SHA512 in BIP-32) to compute child keys systematically from a parent root.
  • Public-Key Cryptography: An asymmetric cryptographic system based on hard mathematical problems (like the ECDLP) where private keys sign and public keys verify.
  • Hashing: One-way cryptographic functions that map arbitrary-length inputs to fixed-length outputs (e.g., Keccak-256) with no feasible inverse.
  • Checksums & Encoding: Mechanisms like EIP-55 that append error-detection markers and format byte arrays for safe transmission and user display.

The evolution of these cryptographic standards spans several decades of foundational research and blockchain development:

Keccak-256 vs. SHA3-256

Although historically related and sharing the same underlying design family, Ethereum's Keccak-256 and the final NIST-standardized SHA3-256 are not identical. Ethereum adopted the Keccak function before NIST finalized its parameter padding and domain-separation conventions, resulting in differing hash outputs for the same input.

4. Why Use Multiple Primitives Instead of One?

The modular design of Ethereum wallets avoids relying on a single monolithic algorithm because each layer solves a distinct engineering and security problem:

  • BIP-39/32/44 handle key management, backup usability, and hierarchical organization.
  • secp256k1 guarantees mathematical trust and digital signature authenticity.
  • Keccak-256 provides cryptographic compression, collision resistance, and one-way address mapping.
  • EIP-55 acts strictly as a human-error checksum mechanism for address transcription.

Combining these specialized primitives ensures optimal performance, strict security boundaries, and robust user experience across the entire lifecycle of a transaction.
