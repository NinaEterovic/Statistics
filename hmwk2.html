HMWK 2 — From Wallet Seed to Ethereum Address

Hashing, Key Derivation and Cryptographic Primitives

Statistical Properties and Historical Context

1. Introduction

An Ethereum wallet allows a user to control blockchain accounts through cryptographic keys. A wallet does not need to store a separate, independently generated private key for every account. Instead, many wallets use a deterministic system in which a mnemonic phrase is converted into a seed, and a hierarchy of private and public keys is derived from that seed.

The resulting Ethereum address is a shorter, public identifier derived from a public key. A checksum convention can then help users detect certain typing errors when copying or entering the address.

This homework examines the standards and cryptographic primitives used in this process, explains their different purposes, and discusses the statistical properties of the resulting values.

Main idea: Key derivation, public-key cryptography, hashing, checksums and encoding are different operations. They work together, but they are not interchangeable.

2. The Ethereum Wallet Pipeline

A common hierarchical deterministic wallet follows the pipeline below. The exact implementation may vary between wallets.

Mnemonic Phrase A sequence of words representing wallet entropy
↓
BIP-39: Seed Generation Mnemonic and optional passphrase → 512-bit seed
↓
BIP-32: Master and Child Keys Hierarchical deterministic key derivation
↓
BIP-44: Derivation Path Selects the account, change branch and address index
↓
Private Key A secret scalar used in elliptic-curve cryptography
↓
secp256k1 Private key → corresponding public key
↓
Keccak-256 Hashes the 64-byte public-key coordinates
↓
Ethereum Address The final 20 bytes of the hash
↓
EIP-55 Mixed-case checksum representation

How the steps fit together

  1. Mnemonic and seed: BIP-39 converts a mnemonic sentence and an optional passphrase into a binary seed.
  2. Key derivation: BIP-32 uses the seed to construct a master key and derive child keys. BIP-44 defines a conventional path structure for organizing accounts and addresses.
  3. Public-key cryptography: secp256k1 maps a private scalar to a public point on an elliptic curve.
  4. Hashing: Keccak-256 transforms the public-key coordinates into a 256-bit digest, from which the Ethereum address is obtained.
  5. Checksum representation: EIP-55 uses the hash of the lowercase hexadecimal address to determine which alphabetic characters should be uppercase.
Important distinction: EIP-55 does not encrypt an address, change its underlying 20 bytes, or authenticate its owner. It provides a convention for detecting certain errors in the written representation.

3. BIP-39 — Mnemonic Phrase and Seed Generation

BIP-39 specifies how computer-generated entropy can be represented as a sequence of human-readable words and how that mnemonic can be converted into a binary seed.

Mnemonic generation

In the standard procedure, an entropy value is generated first. A portion of its SHA-256 hash is appended as a checksum. The resulting bit sequence is divided into groups of 11 bits. Each group selects one word from a standardized list of 2048 words.

Mnemonic construction:

Checksum length = ENT / 32

Total bits = ENT + ENT / 32

Number of words = (ENT + ENT / 32) / 11

The standard supports entropy sizes from 128 to 256 bits in increments of 32 bits. These correspond to mnemonic lengths of 12, 15, 18, 21 and 24 words.

Seed derivation

BIP-39 converts the mnemonic into a 512-bit seed using PBKDF2 with HMAC-SHA512, 2048 iterations and a salt formed from the string "mnemonic" followed by an optional user-supplied passphrase.

PBKDF2-HMAC-SHA512

Password = normalized mnemonic

Salt = "mnemonic" + passphrase

Output = 512-bit seed

The mnemonic checksum helps detect certain mistakes in the phrase. The optional passphrase provides an additional input: different passphrases produce different seeds, even when the mnemonic is unchanged.

Security note: BIP-39 does not make a weak or predictable mnemonic safe. The underlying entropy must be generated securely. A passphrase is not a replacement for strong initial entropy.

4. BIP-32 and BIP-44 — Hierarchical Deterministic Wallets

BIP-32: Hierarchical Deterministic Key Derivation

BIP-32 defines a hierarchical deterministic (HD) wallet. A master key and its descendants can be derived from a single seed. The derivation is deterministic: the same seed and the same derivation path produce the same key.

The master key is initialized using HMAC-SHA512 with "Bitcoin seed" as the key and the BIP-39 seed as the message. The result is divided into two 32-byte parts: one for the master private key material and one for the chain code.

Child keys are derived from a parent key, a chain code and an index. BIP-32 also supports hardened and non-hardened derivation. Extended private keys and extended public keys contain key material and metadata needed for their respective derivation operations.

BIP-44: Standard Derivation Paths

BIP-44 defines a conventional multi-account hierarchy for wallets built on BIP-32. A standard path has five levels:

m / purpose' / coin_type' / account' / change / address_index

A commonly used Ethereum path is:

m/44'/60'/0'/0/0
Path component Meaning
m The master node.
44' Purpose: the BIP-44 hierarchy.
60' Coin type 60, assigned to Ethereum.
0' Account index zero.
0 The external/receiving address branch.
0 The first address index.

The apostrophe indicates hardened derivation. The first three levels in this path are hardened; the final two are not. Wallets may support additional paths or account conventions.

Key management versus cryptography: BIP-32 and BIP-44 organize and derive keys. They do not replace the elliptic-curve operation that turns a private key into a public key, and they do not calculate an Ethereum address.

5. secp256k1 — Public-Key Cryptography

secp256k1 is the elliptic curve used by Ethereum externally owned accounts for public-key cryptography and digital signatures. It is defined over a finite field and has the equation:

\(y^2 \equiv x^3 + 7 \pmod p\)

Here, \(p\) is a large prime defining the finite field. The private key is a secret scalar \(k\), and the public key is the elliptic-curve point:

\(Q = kG\)

In this expression, \(G\) is the standard generator point, and \(kG\) means repeated elliptic-curve point addition. Calculating \(Q\) from \(k\) is efficient, while recovering \(k\) from \(Q\) is computationally infeasible with known classical methods at the intended security level.

This asymmetry is the basis of the elliptic-curve discrete logarithm problem. Ethereum uses secp256k1 with ECDSA signatures to authorize transactions from externally owned accounts.

Public key versus address: The public key is not the Ethereum address. The address is calculated by hashing the public-key coordinates and retaining the final 20 bytes.

6. Keccak-256 — Ethereum Address Derivation

Keccak-256 is a cryptographic hash function that maps an arbitrary-length input to a 256-bit digest. It is used in Ethereum for multiple purposes, including address derivation.

For a conventional uncompressed secp256k1 public key, the public-key representation contains a leading 0x04 byte followed by 32 bytes for the x-coordinate and 32 bytes for the y-coordinate. For address derivation, the leading 0x04 byte is omitted.

Public-key input = x || y (64 bytes)

Digest = Keccak-256(x || y) (32 bytes)

Address = final 20 bytes of the digest

The result is a 160-bit address, conventionally represented as 40 hexadecimal characters preceded by 0x.

A cryptographic hash is deterministic and designed to make it computationally difficult to recover a suitable input from its digest or to find collisions. However, a hash function is not encryption: it has no decryption key and does not provide confidentiality.

7. SHA-2, SHA-3 and Keccak-256

SHA-2 and SHA-3 are families of cryptographic hash functions. Although they serve similar general purposes, they use different internal designs.

Property SHA-2 / SHA-512 Keccak / SHA-3
Design SHA-2 family; SHA-512 uses the Merkle–Damgård construction with a compression function. Keccak uses the sponge construction and the Keccak-f permutation.
Standardization SHA-2 was standardized by NIST in 2001. SHA-3 was standardized by NIST in 2015.
Example output SHA-512 produces 512 bits. SHA3-256 produces 256 bits.
Ethereum address derivation SHA-512 is not used for this step. Ethereum uses Keccak-256, not standardized SHA3-256.

The SHA-3 standard was based on the Keccak design selected through a public competition. The standardized SHA3-256 and Ethereum's Keccak-256 use different domain-separation/padding conventions, so they produce different outputs for the same input in general.

Common mistake: Keccak-256 and SHA3-256 both return 256-bit digests, but they are not interchangeable. Using SHA3-256 instead of Keccak-256 when calculating a standard Ethereum address will generally produce the wrong address.

8. EIP-55 — Mixed-Case Checksum Addresses

An Ethereum address contains 40 hexadecimal characters. EIP-55 defines a mixed-case checksum representation intended to help detect typing errors. The underlying address bytes remain unchanged.

How the checksum works

  1. Remove the 0x prefix and convert the 40 hexadecimal characters to lowercase.
  2. Hash the lowercase ASCII hexadecimal string using Keccak-256.
  3. For each alphabetic address character from a to f, uppercase it if the corresponding hash nibble is at least 8; otherwise, leave it lowercase. Numeric characters do not change.
  4. Add the 0x prefix to the resulting string.

The checksum does not make the address secret, encrypt it, or prove that it belongs to a particular person. It helps identify many accidental changes to the address string.

Because a 40-character address has many possible letter-case combinations, an arbitrary mixed-case string can fail the checksum test. However, EIP-55 is an error-detection convention, not a digital signature or a guarantee that an address is the intended recipient.

9. Key Generation, Derivation, Hashing, Checksums and Encoding

Concept Purpose Example in the pipeline
Key generation Creates new secret cryptographic key material using an appropriate secure process. Generating initial entropy for a wallet.
Key derivation Computes key material deterministically from existing secret material and specified parameters. BIP-39 seed generation and BIP-32 child keys.
Public-key cryptography Establishes a mathematical relationship between private and public keys and supports digital signatures. secp256k1 and ECDSA.
Hashing Produces a fixed-length digest from an input. Keccak-256 for Ethereum address derivation.
Checksum Adds redundancy or a convention that helps detect errors. BIP-39 mnemonic checksum and EIP-55 address casing.
Encoding Represents data in a chosen format, such as hexadecimal or a word list. Hexadecimal Ethereum addresses and BIP-39 mnemonic words.

These operations solve different problems. Derivation organizes and reproduces keys; elliptic-curve cryptography connects private and public keys; hashing produces a compact digest; checksums help detect errors; and encoding makes binary information convenient to represent or communicate.

Encoding is not encryption, and a checksum is not an authentication mechanism. A checksum can help detect an error, but it does not prevent an attacker from deliberately changing data and recomputing a valid checksum.

10. Statistical Properties and Cryptographic Security

The wallet pipeline contains deterministic transformations. If the same valid mnemonic, passphrase, derivation path and algorithms are used, the resulting keys and address are the same. This reproducibility is essential for wallet recovery.

Distribution and apparent uniformity

Cryptographic hash functions are designed so that their outputs have no easily exploitable patterns. For ordinary inputs, the output is expected to exhibit statistical behavior resembling uniform random bits. However, this expectation is not a proof that every finite sample is perfectly uniform.

For an idealized uniformly distributed 256-bit digest, each bit is equally likely to be zero or one. A sample of hashes can therefore be examined by counting bit frequencies, byte frequencies or the distribution of hexadecimal digits.

Expected number of ones in a sample of \(N\) independent ideal random bits:

\(\mathbb{E}[H] = N/2\)

Standard deviation: \(\sigma = \sqrt{N}/2\)

These formulas provide a simple reference for a statistical experiment. Small deviations from the expected frequencies are normal and do not, by themselves, indicate a weakness.

Determinism and correlations

  • Determinism: The same inputs and path reproduce the same address. This is a required property of deterministic wallets.
  • Input-output relationship: The address depends on the derived private key through the public key and hash. This relationship is structured, even when the outputs appear unpredictable.
  • Bit frequencies: A sufficiently large sample can be tested for simple frequency deviations. Passing such a test is not proof of cryptographic security.
  • Avalanche effect: A small input change in a cryptographic hash is expected to change many output bits. This is a useful design property, but it does not mean that every changed input creates an independent output.
  • Address distribution: Ethereum addresses are 160-bit values derived from public keys. Their statistical appearance does not establish that a private key was generated securely.

What can statistics prove?

Statistical tests can reveal certain biases or unexpected patterns in a sample. They cannot establish that a hash function is collision-resistant, that a private key is computationally unrecoverable, or that a mnemonic contains enough entropy.

A weak random-number generator can produce predictable keys even if the resulting hashes appear statistically uniform. Conversely, a secure cryptographic process may produce small deviations in a limited sample simply by chance.

Conclusion about statistical properties: Statistical appearance, deterministic reproducibility and computational security are related but distinct concepts. Cryptographic security relies on carefully studied algorithms, correct implementations and secure entropy—not merely on passing frequency tests.

11. Why Does Ethereum Use Multiple Cryptographic Techniques?

No single primitive provides all the functionality required by a wallet. Each part of the pipeline has a specialized role.

  • BIP-39: Makes backup and restoration more convenient by representing entropy as a mnemonic and defining seed derivation.
  • BIP-32 and BIP-44: Allow a wallet to derive many related keys and organize accounts and addresses from a common seed.
  • secp256k1: Establishes the public-key relationship and supports the signature system used by Ethereum externally owned accounts.
  • Keccak-256: Provides a fixed-length cryptographic digest and is used to derive an address from the public key.
  • EIP-55: Adds a recognizable mixed-case convention that helps users detect many accidental address-entry errors.

Combining these techniques creates a practical system in which keys can be reproduced, signatures can be verified, addresses can be calculated and addresses can be represented in a form that helps users identify some mistakes.

Replacing all these operations with a single hash function, for example, would not provide hierarchical key management, a public/private key relationship, digital signatures and a human-readable checksum all at once.

12. Historical and Chronological Context

The wallet pipeline combines ideas developed over several decades. The following timeline places the principal technologies in approximate historical order.

Year Technology Historical significance
1977 RSA Publicly introduced public-key cryptography based on the difficulty of integer factorization.
2001 SHA-2 / SHA-512 NIST published FIPS 180-2, specifying SHA-2 hash functions including SHA-512.
2012 BIP-32 Proposed hierarchical deterministic wallets and derivation of related keys.
2013 BIP-39 Proposed mnemonic codes for generating deterministic wallet seeds.
2014 BIP-44 Proposed a multi-account hierarchy and standardized derivation-path structure.
2015 SHA-3 NIST standardized SHA-3, based on the Keccak design.
2016 EIP-55 Proposed a mixed-case checksum convention for Ethereum addresses.

This timeline shows how modern wallets combine older public-key cryptography and standardized hash functions with later wallet-specific standards. The standards solve different problems and were not all designed at the same time.

13. Practical Wallet Exploration

Wallet software such as MetaMask, Rabby, Exodus and Rainbow provides a practical way to observe how wallet accounts are organized. The user interface usually hides the underlying cryptographic calculations, but the concepts can be understood by examining account creation, account recovery and address display.

A safe practical investigation can focus on the following:

  1. Observe how a wallet presents an account address and how the address is represented in hexadecimal.
  2. Examine how additional accounts or addresses can be associated with a wallet.
  3. Study the role of the recovery phrase and why it must be kept secret.
  4. Compare the displayed address format with the EIP-55 mixed-case checksum convention.
  5. Explain how a derivation path can select a particular key within a hierarchical wallet.
Security precaution: Never enter a real recovery phrase or private key into an online demonstration, a third-party website, or a homework submission. Do not publish wallet secrets. For experiments requiring actual values, use synthetic examples or an isolated test environment.

14. Conclusion

An Ethereum wallet is built from several complementary cryptographic components. BIP-39 converts a mnemonic and optional passphrase into a seed. BIP-32 and BIP-44 define how related keys are derived and organized. The secp256k1 curve establishes the public-key relationship, and Keccak-256 is used to calculate an Ethereum address from the public key. EIP-55 then provides a mixed-case representation that helps detect certain typing errors.

These operations are deterministic when their inputs and parameters are fixed, which makes wallet recovery possible. Nevertheless, deterministic output does not mean that the secret key can be recovered efficiently from the public address. The security of the system depends on secure entropy, correct implementations and the computational properties of the underlying cryptographic primitives.

Statistical analysis can help identify simple irregularities in sample outputs, but it cannot replace cryptographic security analysis. The central lesson is that key management, public-key cryptography, hashing, checksums and encoding have different purposes and must work together to form a functional wallet system.
