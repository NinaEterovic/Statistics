Homework 2 — ECC Toy Scheme, Caesar Cipher & Cryptanalysis

Implementation, experimental tests, and comparison of key-space attacks

1. Toy elliptic-curve encryption and decryption

This demonstration uses a small elliptic curve for educational purposes. It is not standard secp256k1.

E: y² = x³ + 7 (mod 17) G = (1, 5) Private key d = 6 Public key Q = dG = (5, 8)

Because the field is tiny, this is an educational toy example only. It is not secure and must not be used to protect real data. We use an ElGamal-style construction on the subgroup generated by G. Letters A–H are encoded as G, 2G, …, 8G. The example message is BAD.

Algorithm

  1. The receiver chooses private scalar d and publishes Q = dG.
  2. For each encoded message point Pm, the sender chooses ephemeral scalar r and computes C1 = rG and C2 = Pm + rQ.
  3. The receiver computes Pm = C2 − dC1 and decodes the recovered point.
Press the button to run the ECC toy example.

The point group has a small order, so only a small alphabet subset is used. Real message encoding requires a carefully designed encoding and a secure, standardized encryption construction.

2. Caesar cipher: encryption and decryption

Caesar shifts each English letter by a fixed key k. Non-letters are preserved.

Eₖ(x) = (x + k) mod 26 Dₖ(x) = (x − k) mod 26
Press the button to run the Caesar cipher.

3. Comparison of the schemes

Feature Caesar cipher Toy ECC ElGamal-style scheme
Key role One shared shift k is used for encryption and decryption. Public key Q = dG is used for encryption; private scalar d is used for decryption.
Key space 26 shifts, including the ineffective zero shift. Only a handful of scalars are used in this toy example, so the key space can be searched.
Encryption/decryption Simple modular shifts on letters. Elliptic-curve point operations and reversible message encoding.
Statistical properties Substitution preserves letter counts and patterns, merely relabeling letters. Point ciphertexts do not directly preserve letter frequencies in the same way, but this tiny toy scheme is not secure.
Main weakness Tiny key space and preserved language statistics. The intentionally tiny key space and toy construction/encoding.

4. Statistical cryptanalysis of the Caesar cipher

The attacker tests every possible shift and scores each candidate plaintext against typical English letter frequencies using a chi-squared statistic. The candidate with the lowest score is selected. This is not a guarantee: very short or non-English messages may produce a wrong key.

5. Brute-force attack on the restricted ECC key space

The public key is Q = dG. An attacker can test each candidate d′ in the allowed small range and compare d′G with Q. This recovers the private scalar because the toy key space is deliberately tiny.

For d′ = 1, 2, …, 8: compute Q′ = d′G. If Q′ = Q, output d′.
Target public key: Q = (5, 8). Press the button to search candidates 1–8.

For a properly generated secp256k1 private key, the effective key space is on the order of 2²⁵⁶ candidates. Exhaustive search is infeasible. This conclusion concerns brute-force search; it does not mean every ECC-based construction is automatically secure. Implementation mistakes, poor randomness, or an unsuitable protocol can introduce other weaknesses.

6. Discussion and limitations

  • Caesar attack: The attacker exploits redundancy in natural language. It may work without knowing the key beyond the 26 possible shifts, but it becomes less reliable on short text.
  • Toy ECC attack: The attacker uses the public key and enumerates a restricted private-key space. It is an algebraic brute-force search, not a language-statistics attack.
  • Length matters differently: More Caesar ciphertext generally provides more frequency evidence. For the ECC brute-force attack, the main factor is the number of candidate keys, not the message length.
  • Limitations: English frequency data may not work well for other languages or unusual text. The ECC example uses a tiny curve and limited alphabet mapping solely to demonstrate the operations; it is not a production cryptosystem.

Conclusion: Caesar is vulnerable because it has only 26 shifts and preserves language statistics. The toy ECC example is vulnerable because its private-key range is intentionally small. A properly configured ECC scheme uses a sufficiently large key space, making exhaustive key search impractical, assuming the surrounding protocol and implementation are sound.
